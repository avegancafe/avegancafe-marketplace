The four moments that matter

Critical, customer-impacting milestones

Everything else on the map is machinery. These are the points where a customer's reality changes — and note how late (and how quietly) most of them arrive.

A · ~selectable

Network appears & is selectable

After provider data migrates to Postgres, the network quietly shows up in the dropdown — scoreless and unannounced. “The network is selectable, but there are maybe no scores and they haven't gotten the email yet.” Exact gate unconfirmed; placement approximate.

after handoff · before any scores · before any email
B · scores

Scores become visible

Until the adequacy tables fill, the scorecard API literally 404s (“not yet available”). Scores land mid-to-late chain — and a deploy-triggered re-run can still flicker them blank → partial → full.

late in the score chain · order vs C varies by tenant flag
C · reporting

Reporting data available

reporting_data_available_at is stamped, queued PDFs fire, and report building unblocks. Whether B and C are one moment or two is unresolved even inside J2 — it depends on a per-tenant flag.

after the 6–14 min reporting hop
D · told

The customer is finally told

“Your network is ready” (or “…but we found some issues with your data”) is now the terminal chain step — sent after completed_at, stamped at-most-once, and once sent the run can never auto-restart. Initiator only; teammates never hear a thing.

the very last step · typically ~45 min after upload
📨

#1 · Kickoff

“We are processing your network.” Sent at button-press — before the queue even starts. Initiator only.

skipped for SFTP feeds & recipient-less tasks · prod only
🎉

#2 · Ready

“Your network is ready in J2.” Terminal step, after everything durably commits. At-most-once.

stamps completion_notified_at → “never restart after telling them”
🧐

#3 · Ready, with issues

“Inaccurate data found for <network>” — same moment as #2, different copy when a troubleshooting file exists.

copy gated on the validation results file (NAVY-1142)
🚨

#4 · Problem (maybe)

“Action Required: Problem processing your network.” Fired from exactly 5 call sites — and at least 7 failure paths send nothing. Not deduped: can arrive twice.

the DB's errored_at is more reliable than this email

Scar tissue · 2026

War stories the pipeline now guards against

Three incidents shaped today's ordering and guardrails. Toggle 😈 gremlin mode on the map to see where each one bit.

🫠

April — the silent wedge

Pipeline workers quietly stopped consuming; pods looked healthy for hours. Customers got kickoff emails, then… nothing, on a filing deadline day.

✓ fixed: real liveness probes → ~8 min auto-recovery (#2401/#2406)
📬

June 10 — 26 false failure emails

A starved reporting queue stranded 26 fire-and-forgotten chains ~15 h; a blind bulk re-kick made the drained originals lose snapshot races → 26 “your network failed” emails for healthy networks, and one customer's re-upload loop.

✓ fixed: superseded attempts now stand down silently (#2805) + 12 h watchdog tier (#2807)
🫥

June 24 — ready… then blank

A deploy re-delivered a finished-but-unacked run: customer got the ready email, then watched data go blank → partial (east coast only) → full on refresh.

✓ fixed: email moved to the terminal step + “once told, never restart” (#2957)
